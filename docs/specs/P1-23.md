## What changed since `phase-1-tickets.md`

Original P1-23 (lines 865–892) is the closest of the three tickets in this trio to the as-written scope. Confirmations:

1. **P1-20 ships the substrate immediately before this.** Substrate dependencies (`runFeature`, `createSuggestion`, `acceptSuggestion`, `<AiSuggestionPanel>`, provider abstraction, budgets) are all in place. This ticket is purely the first feature.
2. **Subscriber runs synchronously in Phase 1.** The `finance.expense.created` event fires inside the originating `createExpense` action's `postCommit` (or equivalent post-tx hook). The subscriber's body — load expense, build prompt, call `runFeature`, write `ai_suggestion` — runs inline in that same async context. Phase 5 wraps this in pg-boss with no module surface change. **Verify whether `finance.expense.created` is emitted synchronously or queued today** — current state is the synchronous activity-emit pattern (`emitFinanceEvent`), so subscribers are wired by direct function call from the action's post-commit, not a real bus. This is fine for Phase 1.
3. **Confidence threshold default = 0.6.** Below threshold, the suggestion row is STILL written (so we can audit and tune later) but the `<AiSuggestionPanel>` filter passes `minConfidence: 0.6` to the tRPC query so low-confidence rows are hidden from the UI. Decoupling: storing every suggestion lets us measure recall; the UI filter is a soft visibility threshold the dev can tune.
4. **Accept path: UI calls `acceptSuggestion` then `applyAccountSuggestion`.** Not a subscriber. Simpler. The two server actions fire from one button click; failure of either is surfaced to the user. Rationale: dispatching via an `ai.suggestion.accepted` subscriber introduces async-ness for a UX that should be synchronous (user clicks Accept; expense's category badge updates immediately).
5. **The prompt MUST include the org's CoA.** Per the original ticket's scope line and §3.11 — we don't hardcode account names; we pass the tenant's active, non-system-role, expense-relevant accounts to the LLM as JSON. The model returns an `id` from that exact set or `null` if no good fit.
6. **Per-kind payload schema lives in `lib/prompts/categorizeExpense.ts`** alongside the prompt template — keeps the schema and the prompt that produces it next to each other.

### Subscriber — `src/modules/ai/events/subscribers/categorizeExpense.ts`

```typescript
// Wires into the finance.expense.created event. Phase 1: called directly
// from finance/actions/expenses.ts createExpense's postCommit thunk.
// Phase 5: pg-boss dispatches; same function body.

export async function onExpenseCreated(payload: {
  organizationId: string;
  expenseId: string;
  triggeredByUserId: string;
}): Promise<void> {
  // 1. Load expense via finance.api.getExpense (the public finance api).
  //    Skip immediately if expense.chartOfAccountsId is already set
  //    AND expense.metadata.confidenceLow is not true. The first user-facing
  //    iteration only runs categorization when account is NULL — the
  //    'confidence-low flag' from phase-1-tickets.md is a Phase 5 extension.
  if (expense.chartOfAccountsId) return;

  // 2. Load candidate CoA rows: org-scoped, accountType='expense' OR
  //    'cost_of_goods_sold', is_active=true, system_role IS NULL, deleted_at IS NULL.
  //    NULL system_role excludes the math accounts (cash_operating, employee_payable,
  //    owner_draws, ar_default) — those are never expense categories.

  // 3. Build the prompt via buildCategorizeExpensePrompt (lib/prompts/categorizeExpense.ts).
  //    Input: { description, amountCents, currencyCode, payeeName, candidates: CoaCandidate[] }.

  // 4. Call ai.runFeature({featureName: 'expense-categorizer', prompt, responseSchema}).
  //    On result.success=false (budget, feature disabled, provider error) — return silently.
  //    Per ADR-0003 §3.4, AI failures are non-fatal to the expense.

  // 5. Parse result.data.structured against categorizeExpensePayloadSchema.
  //    If validation fails — return silently (a malformed AI response is logged in ai_runs;
  //    no suggestion row is written).

  // 6. If parsed.proposedAccountId is NOT in the candidate set's id list, refuse to
  //    write the suggestion (hallucination guard — the LLM made up an account id).
  //    Log a structured warning into ai_runs (via metadata or a follow-up update).

  // 7. Call ai.createSuggestion({
  //      aiRunId: result.data.aiRunId,
  //      entityTable: 'finance_expense_entries',
  //      entityId: expenseId,
  //      kind: 'categorize_expense',
  //      payload: parsed,
  //      confidence: parsed.confidence,
  //    }).
  //    No expiry in Phase 1 (suggestions linger until user decides; Phase 5 may
  //    auto-expire after 30 days).
}
```

The hallucination guard (step 6) is non-negotiable. LLMs occasionally invent UUIDs that look plausible. We trust nothing; the proposed id must be in the candidates we sent.

### Wire-up — `finance/actions/expenses.ts`

The `createExpense` action (existing) gets a postCommit thunk that imports and calls `onExpenseCreated`. Phase 1 fires synchronously; per the `postCommit` discipline (P1-14), a thrown error in the thunk does NOT roll back the expense. This is the right semantics — an AI failure must not block expense creation.

Verify: today's `createExpense` may already use a non-`postCommit` event-emit path (synchronous `emitFinanceEvent` inside the tx). The AI call MUST move to post-commit. If `createExpense` doesn't have a `postCommit` thunk yet, add one for this hook.

**If `updateExpense` later changes a categorized expense's `chartOfAccountsId` back to NULL** (rare, but possible), the same subscriber should fire on `finance.expense.updated` with a payload check. Phase 1 covers ONLY `finance.expense.created`; update-triggered re-categorization is a Phase 5 enhancement. Document in PROGRESS.md §7.

### Prompt template + payload schema — `src/modules/ai/lib/prompts/categorizeExpense.ts`

```typescript
import { z } from 'zod';

export const categorizeExpensePayloadSchema = z.object({
  proposedAccountId: z.string().uuid().nullable(),
  confidence: z.number().min(0).max(1),
  reasoning: z.string().min(1).max(500),
});

export type CategorizeExpensePayload = z.infer<typeof categorizeExpensePayloadSchema>;

export type CoaCandidate = {
  id: string;
  accountNumber: string;
  accountName: string;
  accountSubtype: string;
};

export type CategorizeExpenseInput = {
  description: string;
  amountCents: number;
  currencyCode: string;
  payeeName: string | null;
  candidates: CoaCandidate[];
};

/**
 * Returns { systemPrompt, userPrompt, responseSchema }.
 *
 * Notes for prompt design:
 *   - System prompt is short, role-locking ("You are an accounting assistant
 *     categorizing expenses for a small business...").
 *   - User prompt lists the expense + the candidate accounts as JSON. The
 *     model returns structured output matching responseSchema.
 *   - We ask explicitly: "If no candidate is a clear fit, set proposedAccountId
 *     to null and confidence to 0." This is the guard against
 *     low-quality forced answers.
 */
export function buildCategorizeExpensePrompt(input: CategorizeExpenseInput): {
  systemPrompt: string;
  userPrompt: string;
  responseSchema: Record<string, unknown>;
};
```

The response schema is a JSON-Schema-style object that both Anthropic (tool_use) and OpenAI (response_format json_schema) understand. Per the P1-20 provider contract, the substrate translates this to whichever native shape the active provider expects.

### Apply action — `src/modules/finance/actions/apply-account-suggestion.ts`

```typescript
'use server';

export const applyAccountSuggestion = defineAction({
  permission: { module: 'finance', action: 'write' },
  audit: { table: 'finance_expense_entries', action: 'update' },
  schema: z.object({ suggestionId: z.string().uuid() }),
  handler: async (input, ctx) => {
    // 1. Load the suggestion. Assert kind='categorize_expense'. Assert status='accepted'
    //    (called AFTER acceptSuggestion). Org check.
    // 2. Parse suggestion.payload via categorizeExpensePayloadSchema.
    //    If proposedAccountId is null, throw — there's nothing to apply.
    // 3. Re-verify the proposed CoA id still belongs to the org and is active
    //    (the LLM ran days ago; the account may have been retired since).
    // 4. UPDATE finance_expense_entries SET chart_of_accounts_id = proposedAccountId
    //    WHERE id = suggestion.entityId AND organization_id = ctx.organizationId
    //    AND chart_of_accounts_id IS NULL (idempotency — don't overwrite a value
    //    the user manually set in the gap between AI suggesting and user accepting).
    //    If the update affects zero rows, return a soft warning in the result
    //    ("Expense already categorized — suggestion no longer applicable").
    // 5. Emit 'finance.expense.categorized' activity with metadata.via='ai_suggestion'.
    // 6. Return { expenseId, chartOfAccountsId }.
  },
});
```

**This is the only place a category gets written via the AI flow.** Per ADR-0003 §3.4 — AI proposed; user accepted; a normal `defineAction` writes the business data. The audit log row captures the user as actor, not the AI.

### `<CategorizeExpenseSuggestion>` renderer — `src/modules/finance/components/CategorizeExpenseSuggestion.tsx`

Client Component. Implements the `AiSuggestionRenderer` interface from P1-20.

- Renders the proposed account ("Office Supplies — 6500") with the AI's reasoning in a subdued tooltip.
- Renders confidence as a small label (e.g., "AI confidence: 87%").
- Two buttons: Accept (primary) → calls `acceptSuggestion(id)` then `applyAccountSuggestion({suggestionId: id})` sequentially; on success, optimistically removes the panel and the parent page re-fetches the expense (or revalidates). Reject (secondary) → calls `rejectSuggestion(id)`; panel disappears.
- Failure of `applyAccountSuggestion` after a successful `acceptSuggestion`: the suggestion is marked accepted in DB but the expense isn't updated. UX: show toast with the error and an explicit "The suggestion was marked accepted but the account couldn't be applied — please pick the account manually." Rare; surfaces honestly.

## Notes for implementer

- **This ticket validates P1-20 end-to-end.** If P1-20's substrate has a hole, you'll find it here. When you find one, push the fix into P1-20 (update its spec + source if shipped, or its source if pre-merge) — do NOT patch around it locally in `categorizeExpense.ts`.
- **The runtime contract that matters is `runFeature → ai_runs row → result.data.aiRunId → createSuggestion(aiRunId)`.** Both rows commit; the suggestion links to the run that produced it. The audit_log captures both writes. This trail is the substrate's reason for existing.
- **The hallucination guard is the second-most-important line of code in this file.** (The first is "never write business data directly.") LLMs hallucinate UUIDs that look real. The guard: `if (!candidateIds.has(parsed.proposedAccountId)) { log + return }`. Without it, you'd be writing suggestions pointing at made-up account ids, the user clicks Accept, `applyAccountSuggestion` re-verifies and refuses — but the user already saw a suggestion that looked fine. Catch it earlier.
- **Don't `import Anthropic from '@anthropic-ai/sdk'`** in the prompt file or the subscriber file. The P1-20 ESLint rule will fire. The only place those SDKs are imported is `src/modules/ai/lib/providers/`. Your subscriber calls `ai.runFeature(...)`. The provider abstraction handles SDK choice.
- **The prompt template is data, not code.** Future tickets may want to A/B prompts; future tickets may want to seed a `prompts` table. Phase 1 keeps it as a TS string in `lib/prompts/categorizeExpense.ts` — but write the string with a `feature_version: 1` marker and consider it the v1 prompt. When Phase 5 wants to experiment, that marker is the cue to migrate.
- **The system_role candidate filter is load-bearing.** A user asking the AI to "categorize this expense" is implicitly asking "into which of my real expense categories?" If the AI ever proposes `cash_operating` (account 1000), every journal post downstream breaks. The system-role filter excludes that whole class. The hallucination guard is the second wall — if the LLM ignores instructions and produces an id we filtered out, the guard catches it.
- **`<AiSuggestionPanel>` is `'use client'`.** It fetches via tRPC. The renderer prop accepts a server-side path doesn't exist — pass a Client Component for `CategorizeExpenseSuggestion`. Per §6.3 the page itself is a Server Component; the panel is the client island.
- **Confidence is a numeric, not a percent.** DB stores 0.0000–1.0000. UI multiplies × 100 for display. Don't store 87 or 0.87 with type ambiguity.
- **You are the user of P1-20. If your authoring experience is bad, that's a P1-20 bug.** Examples: if `runFeature`'s error cases aren't enumerated, you can't write the silent-return logic correctly. If `<AiSuggestionPanel>`'s `renderers` prop has the wrong shape, your renderer doesn't slot in. Patch P1-20 (the spec + source) until your work here is straightforward.

## What changed since `phase-1-tickets.md`

Original P1-20 (lines 768–799) is mostly intact. Confirmations against the current repo:

1. **ai module doesn't exist yet.** `src/modules/ai/` is brand new in this ticket. No retrofit.
2. **`pgvector` extension was enabled in P1-02 / migration scaffold** per data-model §11 prerequisites. Verify on first commit; if not, this ticket adds the `CREATE EXTENSION IF NOT EXISTS vector;` line to the migration.
3. **No ESLint config exists yet.** The `no-restricted-imports` rule from conventions §9.1 lands here, in a new `eslint.config.mjs` file scoped to the `apps/web` workspace. `apps/web/package.json` has a `lint` script but no rule file — confirmed via the file listing.
4. **`pg-boss` is not installed and won't be for this ticket.** Per ADR-0003 §3.3, the subscriber pattern is "runs in a pg-boss job." In Phase 1, subscribers run synchronously inside the source event-emitter call (i.e., AI subscribers fire from inside the originating mutation's `postCommit` thunk — NOT inside the tx — preserving the "external side effect" boundary). Phase 5 swaps to pg-boss with no module-surface change.
5. **Provider abstraction is the load-bearing piece.** Spec it tightly so P1-23 can swap from Anthropic to OpenAI by changing one row in `ai_features` (a config table introduced here — see "Feature registry" below).
6. **`ai_features` is the one schema addition beyond data-model §11.** Data-model §11 lists `ai_runs`, `ai_suggestions`, `ai_embeddings`, `ai_budgets`. We add `ai_features` (small reference table — feature_name, provider, model, max_tokens, temperature, enabled). Reason: per ADR-0003 §3.5, "the rest of the codebase calls `ai.run('feature-name', input)` which internally selects the right provider for the configured feature." That selection MUST be data-driven (per §3.11), not a hardcoded switch. The table is the canonical place.

// src/modules/ai/schema.ts
export const aiFeatures = pgTable(
  'ai_features',
  {
    id: id(),
    organizationId: organizationId().references(() => organizations.id),
    featureName: text('feature_name').notNull(),        // 'expense-categorizer'

### Provider abstraction — `src/modules/ai/lib/providers/`

Three files. Pure typed wrappers; no business logic; no DB writes.

**`types.ts`** — the uniform interface every provider satisfies:

```typescript
export type CompleteOpts = {
  model: string;
  maxOutputTokens: number;
  temperature: number;
  systemPrompt?: string;
  /** JSON schema (Anthropic tool_use / OpenAI response_format) for structured output. */
  responseSchema?: Record<string, unknown>;
};

export type CompletionResult = {
  text: string;                             // raw completion text
  structured: Record<string, unknown> | null; // parsed JSON if responseSchema was passed
  inputTokens: number;
  outputTokens: number;
  costCents: number;                        // computed from token counts × per-model cents-per-token
  latencyMs: number;
  rawResponse: unknown;                     // for debugging / persisting to ai_runs.completion
};

export type AiProvider = {
  name: 'anthropic' | 'openai';
  complete(prompt: string, opts: CompleteOpts): Promise<CompletionResult>;
  embed(text: string, model: string): Promise<{ embedding: number[]; inputTokens: number; costCents: number }>;
};
```

**`anthropic.ts`** — wraps `@anthropic-ai/sdk`. Implements `AiProvider`. Per-model cost table (input + output cents per million tokens) lives as a `const` map in the same file. Lazy SDK client init (the SDK is heavy; instantiate once on first call).

**`openai.ts`** — wraps `openai`. Same shape. Same cost table approach.

**`select-provider.ts`** — pure resolver: given a feature row (provider name + model), returns the matching `AiProvider` instance. One switch on `provider`. This is the ONLY switch on provider name in the entire codebase.

The "tests prove they're interchangeable" assertion lives in `tests/unit/ai-providers.test.ts` — see verify script + tests.

### Budget enforcement — `src/modules/ai/lib/budget.ts`

```typescript
export class BudgetExceededError extends Error {
  constructor(public readonly module: string, public readonly scope: 'daily' | 'monthly' | 'system_monthly') {
    super(`AI budget exceeded for module '${module}' on ${scope} window.`);
    this.name = 'BudgetExceededError';
  }
}

/**
 * Returns the budget row for (org, module). Throws if no row exists — every
 * module that runs AI MUST have a row seeded. The seed in commit A inserts
 * default rows for every Phase 1 module ('finance', 'billing', 'crm', 'parties',
 * 'ai').
 */
export async function getBudgetForModule(
  tx: FinanceTx,
  orgId: string,
  module: string,
): Promise<AiBudget>;

/**
 * BEFORE every AI call. Sums today's + this-month's costs from ai_runs for
 * (org, feature.moduleBudgetKey). Throws BudgetExceededError if a cap is hit.
 * Also checks system-wide monthly cap (sum across all modules) per ADR-0003 §6.1.
 *
 * "BEFORE the LLM call" is mandatory. A failed budget check produces an
 * ai_runs row with status='budget_exceeded' (logged for visibility) but no
 * outbound API call. Cost is locked to ZERO from a runaway feature.
 */
export async function enforceBudget(
  tx: FinanceTx,
  orgId: string,
  feature: AiFeature,
): Promise<void>;
```

**System-wide cap** per ADR-0003 §6.1 (30000 cents = $300/month total) is enforced as a sum across all modules; stored as a row with `module='__system__'` (reserved key — seed inserts it).

### `runFeature` — the central action

```typescript
// src/modules/ai/actions/run-feature.ts
'use server';

export const runFeature = defineAction({
  permission: { module: 'ai', action: 'write' },
  audit: { table: 'ai_runs', action: 'insert' },
  schema: runFeatureSchema,
  handler: async (input, ctx) => {
    // 1. Load ai_features row (org-scoped). Throw if missing or disabled.
    // 2. Call enforceBudget(ctx.tx, ctx.organizationId, feature) — throws BudgetExceededError or proceeds.
    // 3. INSERT ai_runs row with status='pending' (capture id).
    // 4. Return postCommit thunk that:
    //    - Calls the provider via selectProvider(feature).complete(prompt, opts)
    //    - On success: UPDATE ai_runs SET completion, tokens, cost_cents, latency_ms, status='success'.
    //    - On error: UPDATE ai_runs SET status='error', error_message.
    //    - Returns the CompletionResult (or null on error).
    // The INSERT commits inside the tx; the LLM call fires post-commit and
    // UPDATEs the same row. Caller's tx never waits on the LLM.
  },
});

export const runFeatureSchema = z.object({
  featureName: z.string().min(1),
  prompt: z.string().min(1),
  /** Optional. If passed, the provider attempts structured output. */
  responseSchema: z.record(z.unknown()).optional(),
  /** Optional. Caller's source event for triage. */
  triggeredByEvent: z.string().optional(),
});
```

**Contract for callers** (this is the contract P1-23 consumes — DO NOT change without bumping a major version):

- Caller is always a subscriber, never an end-user route handler (per ADR-0003 §3.3).
- Caller awaits the `ActionResult<CompletionResult | null>`. On `success: false` (budget exceeded, feature disabled, validation failure), caller does NOT proceed to create an `ai_suggestions` row.
- Caller passes `triggeredByEvent` for traceability.
- The `ai_runs` row exists in DB regardless of provider success — budget-exceeded runs have `status='budget_exceeded'` and `cost_cents=0` so dashboards can count denials.

### `acceptSuggestion` + `rejectSuggestion` — public actions

```typescript
export const acceptSuggestion = defineAction({
  permission: { module: 'ai', action: 'write' },
  audit: { table: 'ai_suggestions', action: 'update' },
  schema: z.object({ suggestionId: z.string().uuid() }),
  handler: async (input, ctx) => {
    // 1. Load suggestion. Assert status='pending'. Assert org matches.
    // 2. UPDATE status='accepted', decided_by_user_id=ctx.userId, decided_at=now().
    // 3. Emit 'ai.suggestion.accepted' with metadata.entityTable/entityId/kind.
    // 4. Return suggestion row.
    // CRITICAL: this action does NOT mutate the source entity. Per ADR-0003 §3.4,
    // the consumer (P1-23's `applyAccountSuggestion`) is the action that mutates
    // the expense. The consumer subscribes to 'ai.suggestion.accepted' OR is
    // called directly from the UI's onAccept handler with the accepted suggestion id.
  },
});
```

`rejectSuggestion` is the symmetric path: `UPDATE status='rejected'`, emit `'ai.suggestion.rejected'`. No business mutation.

**Contract for consumers**:
- Accept emits `ai.suggestion.accepted` with `entityTable + entityId + kind + payload` in metadata.
- A per-kind consumer subscribes to this event OR the UI calls the kind-specific apply action directly after `acceptSuggestion` succeeds. P1-23 wires the latter (UI calls `acceptSuggestion` then `applyAccountSuggestion`) — simpler, no subscriber dispatch needed.

### `<AiSuggestionPanel>` component — `src/modules/ai/components/AiSuggestionPanel.tsx`

Client Component. Props:

```typescript
type Props = {
  entityTable: string;     // e.g., 'finance_expense_entries'
  entityId: string;
  /** Per-suggestion-kind renderer. Maps kind → React component that renders
   * the payload and surfaces Accept/Reject buttons. P1-23 registers
   * 'categorize_expense' → CategorizeExpenseSuggestion. */
  renderers: Record<string, AiSuggestionRenderer>;
};

export type AiSuggestionRenderer = React.ComponentType<{
  suggestion: AiSuggestion;
  onAccept: () => Promise<void>;  // calls acceptSuggestion server action
  onReject: () => Promise<void>;  // calls rejectSuggestion
}>;
```

- Fetches `ai.suggestions.listForEntity({ entityTable, entityId, statuses: ['pending'] })` via tRPC.
- Renders nothing if zero suggestions (no empty state — the panel is invisible until AI has something to say; explicit per ADR-0003 §7.2 "asynchronous suggestions feel less magic").
- For each suggestion: lookup `renderers[suggestion.kind]`; render. Unknown kinds render a fallback "AI suggestion — kind unknown" debug card (dev-only; production hides it).
- On Accept: optimistic UI (remove from list), call `acceptSuggestion`. On Reject: same shape.

The empty-state acceptance criterion ("panel renders empty state with no suggestions") from `phase-1-tickets.md` line 799 is satisfied by "renders nothing" — i.e., the panel mounts cleanly with zero data and produces no errors.

## Out of scope

- Any user-visible AI feature (P1-23 ships expense categorization; that's the first user)
- Settings UI for budgets / feature config (Phase 5 — until then, edit `ai_budgets` / `ai_features` via SQL or seed; the verify script proves the row-driven config works)
- Embeddings ingestion pipeline — schema exists, `embed()` provider method exists, but no subscribers populate `ai_embeddings` until Phase 5 (semantic search) or P1-22 if cmd-K scope expands
- pg-boss installation — Phase 5 swap (same call-site discipline as P1-19's renewal entrypoint)
- Multi-suggestion ranking / A/B prompts — Phase 5
- Prompt versioning beyond a `feature_name` string — Phase 5
- Auto-accept rules — explicit non-feature per ADR-0003 §3.4
- Streaming completions — Phase 1 is request/response only; streaming is Phase 5 (chat-style features)
- LangChain or any orchestration framework — explicit reject per ADR-0003 §8.6
- A separate vector DB — explicit reject per ADR-0003 §3.6 / §8.5

## Notes for implementer

- **ADR-0003 is the spec.** Read it cover-to-cover before writing a single line. The interesting decisions (subscriber pattern, no-business-data rule, provider abstraction, pgvector choice) are decided. Don't relitigate.
- **The contract `ai.runFeature(featureName, input, opts)` is consumed by P1-23.** Stabilize the function signature and the `CompletionResult` shape in Commit B; any future change is a breaking change to every subscriber that lands in Phase 5. Get it right here.
- **Budget enforcement runs BEFORE the LLM call.** Not after. Sums today's + this-month's `ai_runs.cost_cents` from a 1-week-of-rows scan that's cheap because `(organization_id, created_at)` is indexed per data-model §11. The check fires inside the tx that opens the `ai_runs` row; if it throws, no row is inserted (defineAction's tx rollback). To get the "log budget-exceeded denials too" behaviour, the `enforceBudget` function inserts the `status='budget_exceeded'` row directly via a savepoint OR inserts BEFORE the check and updates the status if denied. **Implementer's call**: I'd insert-then-check-then-update — one row per attempt, attempt status reflects outcome, dashboards count every attempt. Document the choice in the action handler.
- **The provider abstraction is the load-bearing piece.** Tests must pass with `anthropic.ts` AND `openai.ts` returning structurally identical `CompletionResult` shapes. The verify script proves this via fetch interception + provider-row swap + same-shape assert.
- **Per ADR-0003 §3.4, AI NEVER writes business data.** The verify script's snapshot-rowcounts-before-and-after assertion is the regression bar for this rule. Every future AI feature merge re-runs this assertion. If `acceptSuggestion` ever directly mutates a finance/billing/crm table, the test fires.
- **The "Phase 5 swap to pg-boss" boundary** is the same as P1-19's renewal entrypoint. In P1-20, the postCommit thunk inside `runFeature` IS the durable boundary — the LLM call happens after the tx commits. Phase 5 changes the body of `runFeature.postCommit` from "await provider.complete(...)" to "await pgBoss.send('ai-run', {aiRunId})" and a separate worker handles the call. Caller doesn't change. This is fine for Phase 1 because the originating subscriber is already an async surface (it fired from another mutation's postCommit).
- **No streaming, no agents, no tool-use orchestration in this ticket.** Per ADR-0003 §8.6, that's Phase 5. If you find yourself wanting LangChain, stop.
- **The ESLint rule lands here. Test it.** Future contributors will try to `import OpenAI from 'openai'` in `src/modules/finance/...` because they don't know the rule. The rule catches them; the error message tells them what to do instead.
- This ticket has ONE downstream consumer (P1-23) that lands immediately after. If anything in this spec doesn't match what P1-23.md says it consumes, **fix P1-20 to match the contract**, then update P1-23. The substrate serves the consumer.
